# Buyer-verified respondent confirmation — local candidate, disabled

The Oct5 parent-approved implementation supersedes the dual-checkout-bearer proposal. New and historical buyers use the same user-triggered, single-purpose email verification. Possession of an order URL may request a challenge; it cannot bind respondents. Verification proves current control of the anchored purchase email, not buyer identity, guardianship, or legal consent. Historical orders without trustworthy purchase-contact provenance fail closed; current mutable order email is never a fallback.

`KAMP_RESPONDENT_CONFIRMATION_ENABLED` defaults false. Independently, `KAMP_RESPONDENT_CONFIRMATION_CAPTURE_ENABLED` defaults false and must resolve to boolean true to enable prospective purchase-contact capture. With capture off, both the added checkout row-lock query and anchor encryption/INSERT are skipped before any database/encryption call; ordinary checkout does not depend on the anchor table. Intake enablement never implicitly enables capture. `KAMP_RESPONDENT_CONFIRMATION_ORIGIN` is the exact HTTPS ticketing origin. Config defaults:15minute expiry,60second destination cooldown,5requests/hour/order and destination,5failed code attempts. Application configuration can override these defaults. The existing bridge cohort/payment/event gates also apply. No background challenge issuance/backfill.

The order confirmation page exposes a gated Mantine panel with all active attendees. Buyer requests a code, explicitly selects adult-self/guardian and destination for every attendee, pastes the64hex-character random code from email, and confirms the complete set. Code is never in a URL, localStorage, session cookie or queued job. GET never consumes it. Both POST endpoints require exact Origin, JSON and explicit intent header, with IP throttling. Request responses never return the buyer email or reveal eligibility. The code is hashed at rest in a dedicated purpose/order-bound table; destination bucket is keyed with HMAC. New requests invalidate older unconsumed codes. Failure responses are generic. Axios response/config objects containing request bodies are not retained as mutation results/errors; sensitive fields are excluded from session flashing.

Consumption, source validation, all-sibling assignment and bridge-only outbox insertion share one database transaction. Create-only means existing assignments are never replaced; exact consumed-token/payload replay is a no-op until token expiry. Adult signer name comes from source attendee context. Guardian name/email are buyer nominations, not waiver answers. Normal bridge provisioning rechecks state after commit. No receipt/ticket/payment/webhook email effect is enqueued by confirmation. All-sibling gate retained.

New migration `2026_10_05_000001_create_respondent_confirmation_challenges.php` adds two tables; `2026_10_05_000002_create_order_purchase_contacts.php` adds the encrypted purchase-contact anchor. Both have been rehearsed through the complete native Laravel migration lineage on disposable PostgreSQL16; production is unchanged. Unlike Portal0027, this Laravel migration is auto-discovered on a future deployment: parent must review that schema effect before release. Do not run down after production use. No production configuration, migration, email, grant, deployment or143-person backfill was performed.

## Retention and release controls

`KAMP_RESPONDENT_CONFIRMATION_RETENTION_HOURS` defaults to24hours **after expiry** (minimum1hour). Only strictly older challenges are deleted. Exact replay already stops at expiry. Dead destination buckets are removable only after the retention cutoff, outside the hourly window, with no referencing challenge. Current hourly limits are preserved even if retention is misconfigured below1hour. Purge never accesses/deletes respondent assignments, orders, outbox evidence or canonical waivers.

Native manual command: `php artisan respondent-confirmation:purge --batch=500`. Batch is clamped1–5000. PostgreSQL uses `FOR UPDATE SKIP LOCKED`; challenge deletion commits before destination cleanup to avoid reversing request lock order. Rows locked by an in-flight issue/confirmation are deferred. Output is aggregate deletion counts only; no token/digest/order/signer/email payloads or per-person audit. The optional hourly schedule is gated by `KAMP_RESPONDENT_CONFIRMATION_PURGE_SCHEDULE_ENABLED=false` by default. No scheduler/service was installed.24hours is an eligibility threshold, not a hard maximum while scheduling is disabled or a backlog exists; release must review frequency/batch/monitoring.

Challenge migration adds expiry/destination indexes and order foreign-key integrity (same on-order-delete cascade convention as existing assignment/outbox tables). It has only been applied in disposable test databases, never production. Intake now takes a shared event-row lock along with existing order/attendee/challenge locks to serialize event eligibility changes through confirmation.

## Oct5 independent-review P0 correction: purchase-contact authority

`orders.email` is intentionally receipt-editable and MUST NOT authorize respondent writes. Only when the separate capture flag is explicitly enabled, `OrderPurchaseContactRepository` captures event7's first contact during `CompleteOrderHandler`'s existing transaction, after actual checkout-session comparison, event binding, RESERVED/unexpired state and unprocessed-email checks. An event7 order-row lock serializes competing checkouts; insert is unique, never upsert/ignore. Attendee failure rolls back contact and anchor together. Capture is independent of challenge enablement: enabling it is a separately approved prospective encrypted-contact persistence/checkout effect, including checkouts that have not paid or require no payment. Both flags off adds no anchor persistence or capture lock/failure path to checkout. Turning capture off preserves existing anchors and does not disable verification against those anchors if intake is enabled. Turning it back on never backfills orders checked out while off. Payment and current source eligibility are still required before challenge issuance/consumption; missing anchors always fail closed.

Normalization is explicit: trim whitespace and lowercase the entire validated email address, consistently for delivery and HMAC rate-limit identity. The anchor uses Laravel authenticated encryption with `APP_KEY`; preserve decryption continuity during key rotation. It is never exposed in public resources, queue payloads or logs. The order FK cascades on hard deletion. PostgreSQL rejects ordinary UPDATE even by an owning application connection, but an owner can still DELETE/reinsert or ALTER/DROP the trigger/table. This is not administrator-tamper-proof authority; proposed non-owner intake permissions are SELECT/INSERT only on this table and sequence USAGE. No DELETE, UPDATE, DDL or unrelated-answer access is needed. The ordinary application's existing database role must be reconciled before release; local role rehearsal is not proof of production permissions.

Public self-edit still updates the display/receipt contact and rotates the short ID, but does not change/read the anchor. Challenges requested after such an edit go ONLY to the original purchase mailbox; previously issued codes stay bound to that mailbox. A code and the current order capability are still required. No operator contact-correction API is introduced. A genuine buyer-contact correction requires a separately approved operator recovery process, never receipt authority.

Migration has **no backfill**. Historical mutable email, absence of a self-edit audit, current Stripe billing email and ticket delivery are not trustworthy purchase provenance. Self-service audit is recorded after the email write and operator `EditOrderService` does not use that audit; those records alone do not close historical provenance. Existing143 is an old aggregate, not a fresh audience or an incomplete-waiver count. Recovery remains parent-owned: reconcile original immutable checkout/payment/provider metadata coverage, approve the exact internally bound enrollment cohort or a separate verified operator recovery, then obtain separate exact outreach approval. Never silently insert historical anchors.

The order-bound anchor is durable authority, not an ephemeral verification code; challenge purge deliberately does not delete it. It inherits order deletion lifecycle, with no independently invented long-term retention policy.
